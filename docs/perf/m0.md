# M0 performance note

Date: 2026-10-18. Machine: 12-core x86-64 desktop, NVIDIA GeForce RTX 2060 (Vulkan, driver 610.57),
Chromium 151 headless (software GPU, see below). Reproduce: `just bench` (native), `pnpm bench` in `web/`
(WASM, needs `pnpm preview` or the e2e web server), `just test-gpu` (GPU, prints `PERF` lines).

## CPU engine: native vs WebAssembly

Same functions (`crates/wasm` `bench_*`) run natively and in the browser.

| Workload | Native | WASM single-threaded | WASM threaded (12) | WASM / native |
|---|---|---|---|---|
| GD on 2D Rosenbrock, one core | 87.8 M steps/s | 62.3 M steps/s | 61.8 M steps/s | 1.41× slower |
| Adam, 4 096 starts × 500 steps, 10-D Rastrigin, 1 thread | 0.490 s | 0.648 s | – | 1.32× slower |
| same, all threads | 0.060 s (12 threads, 8.2× speed-up) | – | 0.157 s (4.1× speed-up over WASM 1 thread) | 2.6× slower |

Against DESIGN.md §8: "2D optimizer flat out > 10 M steps/s" — met 6× over in the browser. Native/WASM ratio
target < 1.5× — met single-threaded (1.32–1.41×).

**Finding:** threaded WASM scales worse than native (4.1× vs 8.2× on 12 threads). The likely cause is the
allocator: `run_many` boxes an optimizer and allocates its vectors per start, and WASM's dlmalloc takes a global
lock in the threaded build. Fix in M2 (when many-start mode lands): allocate state once per thread/chunk, or
use a per-thread arena. Not a blocker for M1.

## Frame transport (browser)

Engine worker → render worker, 1 M points per frame (8 MB) plus the trail:

| Transport | Publish cost per frame | Notes |
|---|---|---|
| SharedArrayBuffer triple buffer | 1.12 ms | default on cross-origin isolated pages |
| postMessage with transferable buffers | 4.22 ms | fallback (`?shared=0`) |
| A normal 2D run (≤ 8 200 trail points) | ~0.01 ms | |

Frames published at about 30/s in the stress test, limited by the synthetic swarm's own update
(1 M points of `sin`/`cos` per frame on one thread), not by the transport.

## What couldn't be measured here

Headless Chromium on this machine has no display and gets only a software GPU (SwiftShader). It cannot present
WebGPU to a canvas at all (device lost on the first frame), and its WebGL2 frame rates (1–6 fps) say nothing about
real hardware. **Real-browser frame rates and WebGPU need a check on real browsers**: open the app, press **i**,
read "Display … fps · ms/frame"; `?stress=1000000` adds a million points. Owner's reference machine: MacBook with
Zen and Safari. The UI-thread budget (< 4 ms) is met by construction: the main thread does no per-frame work.
